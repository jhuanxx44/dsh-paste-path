在 macOS 上把 Finder 文件路径粘贴进 DeepSeek Harness

我在 Finder 和浏览器里的 Coding Agent 之间反复遇到一个很小的断点。这里记录它为什么会出现，以及我写的 DSH 插件如何把它补上。

我反复碰到的问题

我通过浏览器界面使用 DeepSeek Harness。工作中一个很常见的动作，是让 Agent 查看本机某个文件，或者进入某个本地目录继续处理。

文件已经在 Finder 里，我也已经选中它并按下 Cmd + C，但回到 DSH 输入框以后，普通粘贴并不会得到它的绝对路径。我还是得选择“拷贝为路径名称”、打开终端、把文件拖进某个输入框，或者手动输入路径。

这些办法都不难。真正让我觉得麻烦的，是每次从“浏览文件”切换到“和 Agent 对话”时，都要重复一次绕路。

/Users/you/code/my-project/src/index.js

为什么普通粘贴拿不到路径

Finder 复制文件时，并不只是把一段绝对路径写成纯文本。它会在 macOS Pasteboard 中写入原生的文件引用列表；在这个场景里，有用的数据可以通过 NSFilenamesPboardType 读取。

另一边，DSH 的输入框运行在浏览器里。浏览器有意限制网页把任意复制的文件转换成本机绝对路径。这条边界是合理的：一个普通网页不应该能够随意知道我的文件系统结构。

所以，这并不是 DSH 文本输入框的 bug。Host 侧掌握着信息，但浏览器侧不应该直接读取它。

我想要的交互

我不想替换普通粘贴，也不想做一个通用剪贴板管理器。我只想增加一个非常窄的交互：

  1. 在 Finder 中选中一个或多个文件、文件夹，按 Cmd + C。
  2. 回到 DSH Web。
  3. 按 Ctrl + V。
  4. 把绝对路径逐行插入当前草稿。

Cmd + V 必须继续承担普通文本粘贴。剪贴板里没有文件路径时，插件也不应该接管 Ctrl + V。

我的解法：一座很小的 Host–Client 桥

我写了 dsh-paste-path，它是一个只面向 macOS 和 DSH Web profile 的插件，由很小的 Host、Client 两部分组成。

1. 在 Host 侧读取原生 Pasteboard

Host 插件通过带 AppKit 的 osascript 读取 NSFilenamesPboardType。如果 Finder 里同时复制了多个文件，它会返回多条路径。它也接受纯文本路径，但前提是每一条非空内容都必须是绝对路径。

插件提供两个本地接口：一个只检查当前是否存在可用路径，另一个在用户真正执行粘贴时返回路径。重复检查会利用 Pasteboard 的 change count；剪贴板没有变化时，不需要反复读取完整内容。

2. 在 DSH Client 侧写入路径

只有检测到有效路径时，Client 扩展才显示一个很小的“Ctrl+V 贴路径”提示。按下快捷键后，它把新路径追加到当前输入框，同时跳过已经存在于草稿中的重复路径。

因此，普通剪贴板行为没有改变。额外的快捷键只服务于浏览器本身无法完成的这一种情况。

边界同样重要

剪贴板属于运行 dsh web 的那台机器。因此，插件的剪贴板接口只接受 loopback 连接，实际写入路径的请求还要通过 same-origin 检查。

  • 插件不会打开或上传复制的文件。
  • 它只向草稿插入绝对路径字符串。
  • 它在 macOS 之外不会启用。
  • 它不是远程 DSH 服务器的文件传输方案。

最后一点尤其重要。如果 DSH 运行在另一台机器上，它的进程就无法读取我这台 Mac 的剪贴板。SSH 端口转发可以让连接在服务器看来仍像 loopback，但它不会自动把客户端剪贴板搬过隧道。远程工作流需要的是文件上传，或者一个明确运行在客户端的配套程序。

安装

这个插件已经发布到 npm：

dsh plugin --profile web add dsh-paste-path

安装后重启 dsh web 并刷新页面。源码、实现说明和当前限制都在 GitHub 仓库中。

这件小事给我的启发

实现很小，因为问题本身也很小。但它恰好落在一条很有意思的边界上：操作系统知道一件浏览器不应该知道的事，而本地 Agent 又确实可以合理使用这条信息。

我的解法不是削弱这条边界，也不是为此构造一个庞大的文件传输系统，而是为一个反复发生的动作增加一座明确、本地、边界可见的小桥。
