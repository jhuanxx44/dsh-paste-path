Pasting Finder file paths into DeepSeek Harness on macOS

I kept running into a tiny break between Finder and a browser-based coding agent. This is what caused it, and the small DSH plugin I wrote to get rid of it.

The problem I kept hitting

I use DeepSeek Harness through its browser-based interface. A common part of my workflow is asking the agent to inspect a local file or work inside a local directory.

The path is already visible in Finder. I can select the file and press Cmd + C, but pasting into the DSH composer does not give me the absolute path. I still have to use “Copy as Pathname,” open a terminal, drag the file somewhere, or type the path by hand.

None of those workarounds is difficult. The annoying part is repeating one of them every time I move from navigating files to talking to an agent.

/Users/you/code/my-project/src/index.js

Why a normal paste cannot do this

Finder does not simply copy an absolute path as plain text. It places a native list of file references on the macOS Pasteboard. In this case, the useful representation is available through NSFilenamesPboardType.

The DSH composer, meanwhile, runs in a browser. Browsers are intentionally restricted from turning an arbitrary copied file into its local absolute path. That boundary is sensible: a normal web page should not be able to discover the layout of my filesystem.

So the missing path is not a DSH text-input bug. The information exists on the host, but the browser side is not allowed to read it directly.

The behavior I wanted

I did not want to replace ordinary paste or add a general clipboard manager. I wanted one narrow interaction:

  1. Select one or more files or folders in Finder and press Cmd + C.
  2. Return to DSH Web.
  3. Press Ctrl + V.
  4. Insert the absolute paths into the current draft, one per line.

Cmd + V must remain normal text paste. If the clipboard does not contain file paths, Ctrl + V should also be left alone.

My solution: a small host–client bridge

I wrote dsh-paste-path, a macOS-only plugin for the DSH Web profile. It has two small halves.

1. Read the native Pasteboard on the host

The host plugin runs osascript with AppKit and reads NSFilenamesPboardType. If Finder has copied several files, it returns several paths. It also accepts plain text only when every non-empty line is an absolute path.

The plugin exposes two local routes: one checks whether a path is ready, and one returns the paths when the user actually pastes. Repeated checks use the Pasteboard change count so the host does not re-read unchanged clipboard contents.

2. Insert paths from the DSH client

The client extension shows a small “Ctrl+V Paste path” hint only when a valid path is available. When I press the shortcut, it appends new paths to the current composer draft and skips paths already present there.

This leaves the normal clipboard interaction alone. The extra shortcut is active only for the one case the browser cannot handle by itself.

The boundary matters

A clipboard belongs to the machine running dsh web. For that reason, the plugin accepts clipboard requests only over loopback and requires same-origin checks for the paste request.

  • It does not open or upload the copied files.
  • It inserts absolute path strings only.
  • It is disabled outside macOS.
  • It is not a solution for a remote DSH server.

That last limitation is important. If DSH runs on another machine, its process cannot read my Mac's clipboard. SSH port forwarding can make the connection look local to the server, but it still cannot move the client machine's clipboard across the tunnel. A remote workflow needs file upload or an explicit client-side companion instead.

Install it

The package is available on npm:

dsh plugin --profile web add dsh-paste-path

After installation, restart dsh web and refresh the page. The source, implementation notes, and current limitations are in the GitHub repository.

What I took away from it

The implementation is small because the problem is small. But it sits at a useful boundary: the operating system knows something the browser should not know, while a local agent can make good use of that information.

The solution was not to weaken the boundary or build a large file-transfer feature. It was to add one explicit, local bridge for one repeated action—and to keep its limits visible.
